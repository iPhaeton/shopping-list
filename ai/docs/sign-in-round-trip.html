The Sign-In Round Trip

Email OTP, from the moment the client picks which Supabase it is talking to, through a six-digit code that leaves the system entirely and comes back through a person, to the header that decides which Postgres role every later query runs as.

01Which Supabase, decided at boot

Before any auth call, pickTarget() chooses a project. The choice is made at runtime rather than at build time because one expo start serves the browser and Expo Go from the same bundle and the same env file — a build-time split would silently send the browser wherever the last build pointed.

This decides more than a URL. It decides where the six-digit code shows up, which is what makes the whole flow drivable end to end in a browser.

Escape hatch EXPO_PUBLIC_SUPABASE_TARGET=cloud npm run web overrides the branch — the way to get two clients on one database.

02The round trip

SignInScreen has two phases in one screen — email, then code — and there is no separate sign-up screen, because shouldCreateUser: true makes the first sign-in of a new address create the account on the same path.

Steps 3 and 4 are the ones worth staring at. The credential leaves the system through an email and re-enters through a person typing it, which is why GoTrue's template choice matters: it sends confirmation to an address it has never seen and magic_link to one it knows, and both must render the token rather than a link.

The asymmetry that hides Override only magic_link and every returning-user test passes while the first sign-in of a fresh address ships an unusable link. See ai/kb/entries/otp-email-templates-carry-the-code.md.

03What the app switches on

AuthState is a discriminated union, not session | null. The third state exists because at launch the answer is genuinely unknown until AsyncStorage has been read, and rendering either stack during that gap flashes the wrong one.

getSession() resolves the launch case once; after that onAuthStateChange is the only writer. Sign-in and sign-out both arrive through that one subscription rather than as return values from the calls that caused them.

Why a union A biometric unlock would land as one new case — { status: 'locked' } — that RootNavigator switches on, instead of an edit at every point that asks "is there a session?"

04What every later request carries

There is one client, created once at module load with the anon key. Signing in does not build a second one — it changes a single header, and that header is the entire difference between the two Postgres roles.

The apikey header is identical in both cases; it is the gateway's concern. It is the bearer token that PostgREST reads, whose role claim it applies with set local role for the transaction, and whose sub claim becomes auth.uid().

Not a security boundary by itself anon matching no rows is a consequence of the policy predicate, not of the role. A using (true) policy plus Supabase's default grants is world-readable to anyone holding the anon key, which ships in the bundle.

05Staying signed in, and signing out

autoRefreshToken keeps the access token alive, but only while a timer is running. On native the token would otherwise expire silently while the app sits in the background, so an AppState listener starts and stops the refresh on foreground and background; the browser tab keeps running and needs no equivalent.

A token that does slip through expired is not a lost write. The outbox classifies a 401 as retryable precisely because supabase-js will have refreshed the token by the next attempt — while a 403, which is row-level security actually refusing, is permanent and drops the write.

Sign-out clears this account's cached lists first, then calls signOut({ scope: 'local' }). The scope is deliberate: the supabase-js default is 'global', which revokes every device, so signing out in a browser would eventually sign out the phone. The outbox is deliberately not cleared — those writes are still owed to the database and flush at the next sign-in.

The one auth error that deletes data A tightened policy does not merely block a write; the 403 it returns takes the queued write off the device, with one error banner to show for it.

Two claims worth keeping apart: the templates are wired correctly in config and confirmed in the dashboard, and device sign-in works end to end against production. As of the last check only the first has been proven — verifying the second needs a brand-new address, then the same address again, to exercise both template paths.
